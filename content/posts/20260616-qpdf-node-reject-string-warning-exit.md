## "PDF post-process failed: undefined"

A document backend renders a spreadsheet-and-docx template to PDF, then post-processes the result: stamp a few images on with [pdf-lib](https://github.com/Hopding/pdf-lib), then encrypt it with [qpdf](https://qpdf.sourceforge.io/) so printing can be locked down. One print endpoint started returning a 501 with this body:

```
PDF 후처리 실패: undefined
```

Translated: *PDF post-processing failed: undefined.* The word that matters is `undefined`, and it survives translation intact.

That `undefined` is not a missing config value or an unset variable. It's a specific, readable signal about *how* the error was thrown — and once you learn to read it, it points straight at the bug. The handler looked like this:

```js
try {
  await pdfPostProcess.applyPostProcess(pdfPath, pdfPath, { stamps, encrypt });
} catch (err) {
  throw new Error(`PDF post-process failed: ${err.message}`);
}
```

`err.message` is `undefined`. In JavaScript, reading `.message` off a value that has no such property gives `undefined` rather than throwing. So `err.message === undefined` means **`err` is not an Error.** Something in that `await` chain rejected with a value that isn't an `Error` object — and whatever real diagnostic it carried got flattened to the string `"undefined"` the moment I interpolated `.message`.

## A library that rejects with a string poisons every catch above it

The encryption step delegated to a small qpdf wrapper library (the version I was on was `node-qpdf2@4.0.2`). It spawns the `qpdf` binary and resolves/rejects a promise on process exit. Reconstructed, its close handler did roughly this:

```js
child.on("close", (code) => {
  if (code !== 0) {
    reject(Buffer.from(stderr.join("")).toLocaleString()); // rejects with a STRING
  }
  resolve();
});
```

It rejects with a **string** — the joined stderr text — not `new Error(...)`. That one decision is the whole bug. A rejected string is a perfectly legal promise rejection, so nothing crashes. But a string has no `.message`, no `.stack`, no `name`. Every `catch` block upstream that does the idiomatic `err.message` gets `undefined`, and the actual qpdf stderr — the one thing that would tell me what went wrong — is destroyed at the point of consumption.

This is the quietest kind of footgun. The library "works." It rejects on failure like it should. It just rejects with the wrong *shape*, and the cost lands three call frames away in code that had every reason to assume a caught value is an `Error`. JavaScript lets you `throw` and `reject` with anything — a string, a number, `null` — and the convention that it's always an `Error` is exactly that: a convention, not a guarantee.

So the first fix isn't even in my code. It's to stop trusting the wrapper's error channel and own the qpdf call myself.

## The second trap: qpdf exits 3 on warnings, and that's not a failure

When I dropped the wrapper and spawned `qpdf` directly, I could finally see the stderr. And it revealed the *real* reason the print failed — which had nothing to do with my stamps or my password handling.

qpdf doesn't use a binary success/failure exit code. It has three states:

| Exit code | Meaning | Output written? |
| --- | --- | --- |
| 0 | clean — no errors, no warnings | yes |
| 2 | errors — could not complete | no |
| 3 | **warnings** — completed with recoverable issues | **yes** |

Exit code 3 is the trap. The PDF *was* produced correctly; qpdf merely grumbled about something recoverable on the way. And PDFs generated by pdf-lib commonly trip those benign warnings — slightly non-canonical structure that qpdf notices, repairs, and complains about while still writing a valid file.

The wrapper's check was `if (code !== 0)`. So every warning-level run — exit 3, output sitting right there on disk, fully usable — got treated as a hard failure and rejected. Combine the two bugs and you get the full picture: a successful encryption with a cosmetic warning was reported as a fatal error, *and* the message explaining it was annihilated into `undefined`.

qpdf has a flag for exactly this: `--warning-exit-0` makes it exit 0 even when it emits warnings. That's the difference between "treat warnings as failures" and "treat warnings as warnings," expressed as one CLI flag.

## The fix: spawn qpdf directly, keep the Error an Error

Replacing the wrapper with a direct `child_process.spawn` call gave me three things at once: warnings stop failing the print, genuine errors throw a real `Error` carrying the full stderr, and a missing binary produces a message a human can act on instead of a generic crash.

```js
const { spawn } = require("node:child_process");

function runQpdfEncrypt(ownerPassword, printMode, inPath, outPath) {
  return new Promise((resolve, reject) => {
    const args = [
      "--warning-exit-0",                 // warnings (exit 3) are not failures
      "--encrypt", "", ownerPassword, "256",
      `--print=${printMode}`, "--modify=none", "--extract=n",
      "--", inPath, outPath,
    ];

    const child = spawn("qpdf", args);

    let stderr = "";
    child.stderr.on("data", (chunk) => { stderr += chunk; });

    child.on("error", (spawnErr) => {
      if (spawnErr.code === "ENOENT") {
        reject(new Error("qpdf not found on PATH — is it installed?"));
        return;
      }
      reject(spawnErr); // already a real Error
    });

    child.on("close", (code) => {
      if (code === 0) {
        resolve();
        return;
      }
      reject(new Error(`qpdf exited ${code}: ${stderr.trim()}`));
    });
  });
}
```

A few things worth calling out:

- **`child.on("error")` and `child.on("close")` are different events.** The `error` event fires when the process can't even start — the classic case being `ENOENT`, the binary not on `PATH`. The `close` event fires when it ran and exited with some code. The wrapper conflated these, so "qpdf isn't installed" and "qpdf ran and warned" came out looking the same. Handle them separately and the failure modes stay legible.
- **The rejection is always a real `Error` with the stderr inlined.** Now the upstream `catch (err) { ... err.message ... }` works as written, because the contract it assumed is finally true.
- The `--encrypt "" ownerPassword 256` positional form is the older qpdf encryption syntax (empty user password, an owner password, 256-bit). qpdf 11+ prefers the flag form `--encrypt --user-password='' --owner-password=… --bits=256 --`; pick whichever matches the qpdf you ship, but verify against your installed version — the positional form is deprecated and, fittingly, a deprecation notice is itself a *warning*, i.e. exit 3.

After this, the integration test that drives the post-processor — encryption applied, printing blocked when `allowPrinting` is false, allowed by default — went 7 for 7. The print that had been 501-ing went through, and the one case that genuinely failed now threw a message I could read.

## The part worth keeping even if you never touch qpdf

Two transferable lessons came out of this, and neither is about PDFs.

**An error message of literally `undefined` is evidence, not noise.** When you interpolate `${err.message}` and get `undefined`, the caught value isn't an `Error` — someone upstream rejected or threw a string, a number, an object literal, something. That's diagnostic on its own. Before you go hunting for an unset variable, look at what shape the thrown value actually has. The fastest way to make these legible is to normalize at the boundary:

```js
catch (err) {
  const message = err instanceof Error ? err.message : String(err);
  throw new Error(`PDF post-process failed: ${message}`);
}
```

That one line would have surfaced the real qpdf stderr immediately, instead of `undefined`, even before I knew the wrapper was the culprit. Treat `err.message` as untrusted: you don't control everything that can land in your `catch`.

**Exit codes aren't binary, so don't write `if (code !== 0)` reflexively.** A whole class of CLI tools — qpdf, rsync, grep, diff — use the exit code as a multi-valued status, where "nonzero" spans "warned but succeeded" and "failed outright." Collapsing that to a boolean turns recoverable warnings into fatal errors. Read the tool's exit-code table before you decide what counts as failure, and reach for the tool's own "treat warnings as success" switch (`--warning-exit-0` here) instead of inventing your own.

The print was never broken. qpdf had been doing its job and saying so politely the entire time — the message just had to survive the trip back up the stack.
